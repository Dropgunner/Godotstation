# SS13 gameplay reconstruction: tgstation criterion, Unitystation bridge

**Checked:** 2026-10-18. **Purpose:** define the observable game we are porting before adding more isolated features. This is a bounded source investigation, not a claim that a full SS13 round was captured or reproduced.

## Evidence boundary

I used REA 3.1.0 `import-reference-source` on a ten-file tgstation corpus at [`f37d36c`](https://github.com/tgstation/tgstation/tree/f37d36c295c4bf991b72647281352f3bd471b335), a four-file Unitystation interaction/round corpus at [`c911581`](https://github.com/unitystation/unitystation/tree/c911581e8354958d664b1e32087053ce43638790), and a three-file Unitystation Engineering corpus at [`b0bb5b7`](https://github.com/unitystation/unitystation/tree/b0bb5b77b33e2e3e61de1a17254664f626834263). REA returned `HistoricalSourceGraph/v1` with `inventory_state: partial`; the tgstation and current Unitystation corpus hashes were `0cc73f0901cd235ad5736886503c355300e1a916acab1a8dd0c4ec8567d77a11` and `625880373692d74a5bae523e6a4203eb6fdced83c275557a273376d63ac067a5`. It hashed and inventoried these files; it did **not** parse DM semantics, execute either game, inspect a shipped binary, or produce gameplay traces. The behavioral statements below come from direct source reading and are marked as such. No source files were copied into this project.

## What the game must let players do

/tg/station describes SS13 as a [round-based roleplaying game on a dangerous space station](https://github.com/tgstation/tgstation/blob/f37d36c295c4bf991b72647281352f3bd471b335/README.md). The essential player path is therefore a shared, consequential shift, not a collection of feature demos. The following are testable reconstruction obligations, not a claim that every tgstation variant behaves identically.

The round criterion also requires consequences of danger and an end condition. The current corpus does not establish a specific tgstation round mode, health/ghost rule, or shuttle path to port. Trace those before specifying exact behavior; do not replace them with a generic host victory button.

## Next complete vertical slice

The first bounded implementation is one source-backed power restoration path: an Engineer fuels and starts a generator, enables storage output, and restores power to an APC-fed lamp that both clients can see. Fuel exhaustion reproduces an outage, and reserve fuel restores power. Server state owns fuel, charge, output, device power, and interaction validation; clients render snapshots and submit intent. The rates remain explicitly playtest-scaled, not source-game parity. Keep the power rules in `src/`, with Godot only as the adapter.

The larger playtest gate remains one two-client ordinary-controls recording of **outage → report → Engineer diagnosis/action → shared recovery → repeat failure/recovery → round end/restart**, plus deterministic power-rule tests and two-client transport evidence. This first loop does not yet pass that full gate. If the device has no observable effect beyond a label, it does not count as a station consequence. See the power Fidelity Contract for verified behavior and remaining gaps.

## Research still needed

- Select and trace one tgstation round mode and its actual end/report path, then compare Unitystation's mode and restart behavior.
- Trace tgstation health/incapacity/ghost/recovery and the corresponding Unitystation path before adding failure consequences.
- Trace tgstation APC/device power behavior and Unitystation's electrical module/network details before setting parity-level numerical power contracts; current playtest rates are intentionally disposable.
- Capture a legal, reproducible two-client runtime scenario if executable reference builds become available. REA reference import alone cannot supply a golden gameplay trace.
